## 一、架构总览

### 1.1 架构模式

本系统采用 **Agentic Workflow** 架构，整体设计遵循以下核心范式：

```
┌───────────────────────────────────────────┐
│              Presentation                 │
│        (Streamlit Web / CLI)              │
├───────────────────────────────────────────┤
│            Orchestration                  │
│      (LangGraph StateGraph)               │
├──────────┬──────────┬────────────────────┤
│  Agent   │ Specialist│  Strategy          │
│  Nodes   │   Nodes   │  & Generation      │
├──────────┴──────────┴────────────────────┤
│              Memory                       │
│       (Facts + Anomalies Tables)          │
├───────────────────────────────────────────┤
│          Infrastructure                    │
│   (LLM Client / Config / Prompts / Utils) │
└───────────────────────────────────────────┘
```

这是一个**有状态的多节点流水线**，不是简单的请求-响应式 ChatBot。每次用户输入触发一轮完整的图执行，状态在节点间传递和累积。

### 1.2 技术选型理由

| 组件 | 选型 | 理由 |
|------|------|------|
| LangGraph | 工作流引擎 | 原生支持条件路由、Fan-out 并行、状态聚合，适合多 Agent 协作 |
| Streamlit | Web 前端 | 快速构建数据密集型 Web UI，原生 Session State 管理 |
| ChatOpenAI (LangChain) | LLM 客户端 | 兼容 OpenAI API 格式，支持 DeepSeek 等第三方模型 |
| TypedDict + operator.add | 状态定义 | 轻量级类型约束，add reducer 自动合并并行节点的输出 |
| Pydantic SecretStr | 密钥安全 | 防止 API Key 在日志中泄露 |
| python-dotenv | 配置管理 | 标准 12-factor app 实践 |

## 三、状态设计：DialogueState

`state_schema.py` 中定义的 `DialogueState` 是系统的**唯一数据中枢**，所有节点通过它交换信息。

### 3.1 状态分类

| 类别 | 字段示例 | 语义 |
|------|----------|------|
| 对话基础 | `round_id`, `max_rounds`, `current_user_text`, `dialogue_history` | 管理多轮对话生命周期 |
| 事实追踪 | `current_facts`, `facts_table` | 当前轮新事实 vs 全局累计事实 |
| 异常追踪 | `current_anomalies`, `anomalies_table` | 当前轮新异常 vs 全局累计异常 |
| 专家分析 | `specialist_results` (Annotated[List, operator.add]) | 并行专家结果自动合并 |
| 风险评分 | `lie_index`, `surface_risk_score`, `risk_explanation`, `dimension_scores` | 多层风险评估 |
| 路由决策 | `routing_decision`, `selected_specialists`, `priority_issue`, `followup_strategy` | 控制流程图走向 |
| 预分析 | `quick_fact_summary`, `quick_signal_summary`, `severity`, `confidence` | 快速分析快照 |
| 经验链 | `specificity_level`, `experience_density`, `generic_answer_flag`, `last_probe_angle`, `used_probe_angles` | 追踪追问深度和角度 |
| 控制流 | `next_action`, `final_report`, `stop_reason`, `target_anomaly_id` | 决定图的下一步走向 |

### 3.2 Annotated Reducer 设计

```python
specialist_results: Annotated[List[Dict], operator.add]
called_specialists: Annotated[List[str], operator.add]
```

使用 `operator.add` 作为 reducer，使得 LangGraph 在 Fan-out 并行执行时能够**自动合并**多个专家的输出，无需手动编写聚合逻辑。这是 LangGraph 的核心机制之一。

### 3.3 状态演变

状态在每轮对话中不是"替换"而是"累积"：`facts_table`、`anomalies_table`、`dialogue_history` 等字段在每轮执行中被追加新数据，实现跨轮的信息积累。

## 四、图工作流设计

### 4.1 节点拓扑

```
START
  │
  ▼
quick_preanalysis          ←── 入口：事实抽取 + 异常检测
  │
  ▼
lightweight_routing_supervisor  ← 决策：是否需要专家？需要哪些？
  │
  ├── (无专家) ──────────────────────────┐
  │                                      │
  └── (有专家) ──→ Fan-out ──→ ┌─────────┤
                   semantic_agent       │
                   logical_agent        │  ← 并行执行
                   domain_agent         │
                   psycho_linguistic_agent ──┘
                                          │
                                          ▼
                                   risk_aggregator   ← LieIndex 计算
                                          │
                                          ▼
                                   strategy_supervisor  ← 继续/终止决策
                                          │
                          ┌───────────────┴───────────────┐
                          ▼                               ▼
                   followup_generation           report_generation
                          │                               │
                          ▼                               ▼
                         END                             END
```

### 4.2 关键路由点

**路由点 1: route_after_routing_supervisor**
- 检查 routing_decision 是否为 `retry_quick_preanalysis`（Schema 解析失败时触发重试）
- 若无选中专家 → 直接跳转到 risk_aggregator
- 否则通过 `route_specialists()` 生成 `Send` 列表实现 Fan-out

**路由点 2: route_after_strategy_supervisor**
- 若 `next_action == "final_report"` → report_generation
- 否则 → followup_generation

### 4.3 Fan-out 实现

```python
def route_specialists(state: DialogueState) -> list[Send]:
    selected = state.get("selected_specialists", [])
    mapping = {
        "semantic": "semantic_agent",
        "logical": "logical_agent",
        "domain": "domain_agent",
        "psycho_linguistic": "psycho_linguistic_agent",
    }
    return [Send(mapping[s], state) for s in selected if s in mapping]
```

`Send(node_name, state)` 是 LangGraph 的并行分发原语：每个 `Send` 对象将当前 state 副本发送给目标节点，所有分支完成后通过 `operator.add` reducer 自动合并结果到下一节点。

### 4.4 图编译

`graph.py` 的 `build_graph()` 函数负责：
1. 创建 `StateGraph(DialogueState)` 实例
2. 注册所有节点
3. 添加边（普通边 + 条件边）
4. 调用 `builder.compile()` 返回 `CompiledStateGraph`

编译后的图可被 Streamlit 和 CLI 共享使用，实现 UI 与逻辑的解耦。

## 五、节点设计模式

### 5.1 统一节点签名

所有节点遵循相同的函数签名：
```python
def xxx_node(state: DialogueState) -> dict:
```

输入是完整的 `DialogueState`，输出是包含状态更新的 `dict`。LangGraph 自动将返回的 dict 合并回全局状态。

### 5.2 节点包装器（node_wrapper.py）

`wrap_node()` 函数通过闭包将所有节点包装为带监控的版本：
- 注入执行耗时计算
- 捕获异常并重新抛出（不吞掉异常，保持 LangGraph 的错误传播链）
- 将输入/输出/耗时/错误记录到详细日志

这使得所有节点无需在业务代码中手动添加日志逻辑。

### 5.3 JSON 输出解析模式

由于所有节点的分析逻辑依赖 LLM 输出结构化 JSON，系统采用统一的三层解析策略（`json_utils.py`）：

1. **直接解析**：`json.loads(text)` — 适用于 LLM 输出纯 JSON
2. **代码块提取**：正则匹配 ` ```json ... ``` ` — 适用于 LLM 输出 Markdown 包裹的 JSON
3. **结构搜索**：搜索第一个 `{...}` 或 `[...]` 匹配对 — 适用于 LLM 在文本中嵌入 JSON

如果三层都失败，`safe_json_parse_with_retry()` 会：
- 调用 `clean_llm_output(aggressive=True)` 进行激进清洗（去除非 JSON 前缀后缀、修复常见格式错误）
- 再次尝试三层解析
- 仍失败则返回默认值并记录错误日志

### 5.4 异常表更新模式

`anomaly_table.py` 是多来源异常合并的核心。设计要点：

- **来源优先级**：不同类型专家的证据权重不同（semantic/logical > domain > psycho_linguistic > quick_detection）
- **更新类型优先级**：reinforce > remain_unresolved > clarify > resolve（更新不会"降级"异常状态）
- **并发安全**：多个专家并行执行时对同一异常的更新通过确定性优先级规则解决冲突
- **追问保护**：每个异常记录 `followup_count`，超过阈值自动标记 `stop_followup=True`

## 六、评分系统设计

### 6.1 风险值计算流水线

```
原始标签 (severity, confidence)
    │
    ▼
normalize_quick_risk_labels()   ← 标准化 + 容错（非法值 → 推断修正）
    │
    ▼
effective_risk_value()          ← V_i = severity_base_score × confidence_weight
    │
    ▼
combine_independent_risk_values() ← LieIndex = 100 × (1 - ∏(1 - V_i/100))
    │
    ▼
determine_risk_level()          ← 低(<30) / 中(30-60) / 高(>60)
```

### 6.2 容错设计

`normalize_quick_risk_labels()` 在处理 LLM 输出的非标准标签时具有降级策略：
- 非法 severity → 根据 `surface_risk_score` 反推合理值
- 非法 confidence → 根据是否有实质性分析内容判断 HIGH/LOW

这使得系统对 LLM 输出格式的不稳定性有一定容忍度。

## 七、追问策略系统设计

### 7.1 策略注册表

`strategy_utils.py` 中的 `STRATEGY_REGISTRY` 是追问策略的单一事实来源。每个策略包含：

```python
{
    "name": "experience_probe",
    "category": "broad_probe",         # 策略大类
    "selection": "...",                 # 路由/Supervisor 如何识别何时选用
    "exec_direction": "...",           # 追问生成器如何执行
    "exec_boundary": "...",            # 追问边界/禁忌
    "trigger_keywords": [...],         # （可选）触发关键词
}
```

### 7.2 经验链角度轮转

对于 `experience_chain` 类策略，有 6 种追问角度循环使用：
1. `process_sequence` — 过程顺序
2. `boundary_judgment` — 边界判断
3. `real_constraint` — 现实限制
4. `counterexample` — 反例/卡点
5. `term_clarification` — 术语澄清
6. `output_evidence` — 产出证据

`normalize_probe_angle()` 确保不会在同一对话中重复使用已用过的角度。

### 7.3 追问生成两阶段

`followup_generation_node.py` 将追问分为：
1. **粗生成**（FOLLOWUP_GENERATION_PROMPT）：基于策略执行指引生成追问
2. **润色**（FOLLOWUP_POLISH_PROMPT）：将问句包装为自然的相亲聊天语句

这种两阶段设计让策略逻辑和表达风格解耦。

## 八、日志与可观测性

### 8.1 日志架构

`utils/logger.py` 中的 `DetailedLogger` 类实现了**两级日志**：

| 级别 | 粒度 | 输出 |
|------|------|------|
| 会话级 | 整个对话 | `session_data` 包含所有轮次、节点、耗时 |
| 节点级 | 单次节点执行 | 输入状态、输出更新、耗时、错误 |

每个会话结束时生成：
- `outputs/reports/session_YYYYMMDD_HHMMSS.json` — 最终报告
- `outputs/logs/` — 详细的节点级执行日志

### 8.2 单例日志

通过模块级 `_logger_instance` 实现全局单例，所有节点共享同一个日志实例，确保一个会话产生一份完整日志。

## 九、评测系统设计

### 9.1 评测流水线

```
benchmark_annotation_template.csv  (人工标注：true_label=real/fake, valid标记)
    │
    ▼
run_benchmark.py
    │  对每条数据调用系统获取 system_score
    │  system_score < 25 → 判为 safe (real)
    │  system_score ≥ 25 → 判为 risk (fake)
    │
    ▼
4 项指标输出:
  - Accuracy（准确率）
  - Fake Recall（虚假样本召回率）
  - False Alarm Rate（误报率）
  - Risk Gap（虚假样本 vs 真实样本的平均分数差）
```

### 9.2 Baseline 对比

`benchmark/baseline/` 提供不使用完整 Multi-Agent 流程的基线评测，用于量化架构带来的增益。

## 十、关键设计决策

### 10.1 为什么用 LangGraph 而不是简单的顺序调用？

- **条件路由**：低风险跳过专家、schema 解析失败重试，这些分支逻辑不适合硬编码顺序
- **Fan-out 并行**：4 个专家可以同时分析，减少总耗时
- **状态管理**：TypedDict + reducer 机制让状态在多节点间自动流转、自动合并

### 10.2 为什么快速预分析单独成为一个节点？

- 减少 LLM 调用延迟：一次调用完成事实抽取 + 异常检测 + 风险标签，而不是三次独立调用
- 信息优势：同一 LLM 调用中可以交叉引用事实和异常做出更准确的判断
- 路由决策依据：表层风险评分决定后续的分析深度

### 10.3 为什么 routing_supervisor 同时使用规则和 LLM？

- 规则处理确定性场景（severity 低、无异常 → 直接跳过），快速且零成本
- LLM 处理复杂场景（多异常混合、边缘案例），利用模型的上下文理解能力
- 规则兜底：LLM 输出非法时回退到规则决策

### 10.4 为什么 lie_index 使用概率乘积公式？

- `1 - ∏(1 - V_i/100)` 保证值域在 [0, 100]
- 多个低风险叠加不会爆炸（与简单求和不同）
- 自然表达"独立证据协同指向风险"的直觉
- 即使全部证据都是 90 分风险，整体也不会超过 100

### 10.5 为什么心理语言学分析不能单独驱动高风险结论？

心理语言学检测的是"软信号"（回避、过度解释等），这些行为本身可能由紧张、性格内向等原因导致，不必然指向欺骗。因此系统设计上将其视为辅助增强信号，而非独立风险来源。

## 十一、扩展点

系统的设计预留了以下扩展点：

1. **新增专家**：在 `nodes/specialists/` 创建新节点 → `graph.py` 注册 → `prompts.py` 添加 Prompt → `score_utils.py` 注册来源
2. **新增追问策略**：在 `strategy_utils.py` 的 `STRATEGY_REGISTRY` 中添加策略定义即可
3. **替换 LLM**：修改 `config.py` 中的 API 配置即可切换到任何兼容 OpenAI API 的模型
4. **新增前端**：`build_graph()` 返回的 `CompiledStateGraph` 可被任何 Python 代码调用，不绑定 Streamlit
