# 项目思路书

## 一、项目背景

随着线上相亲、交友和社交平台的发展，用户在建立关系前往往需要通过聊天了解对方的基本情况，其中职业身份是判断对方生活状态、价值观、稳定性和可信度的重要信息。但在实际交流中，对方的职业叙述通常依赖自我陈述，平台和聊天对象很难直接验证其真实性。

当前相亲交友场景中，职业身份判断主要存在以下问题：

1. 职业身份容易被包装或虚构。用户可以声称自己是医生、教师、公务员、程序员、心理咨询师等，但不一定具备真实从业经历。
2. 人工判断依赖经验。如果普通用户缺少职业常识，很难判断对方回答是否符合真实职业场景。
3. 当前多数聊天机器人只负责生成回复，不具备持续追问、风险分析、证据聚合和报告输出能力。

因此，本项目希望构建一个面向相亲交友场景的多 Agent 职业身份一致性检测系统，通过多轮自然对话分析用户职业叙述是否稳定、具体、符合常识，并给出结构化风险评估。

## 二、项目目标

本项目最终目标是实现一个可以在线运行的“职业身份一致性检测助手”。系统通过自然聊天方式与用户进行 5 到 8 轮对话，在不显得生硬审问的前提下，逐步获取对方职业身份、工作内容、真实经历和关键细节，并判断其职业叙述是否存在异常。

项目希望实现以下效果：

1. 通过多轮对话收集用户关于职业身份的事实信息。
2. 自动抽取用户回答中的职业、岗位、工作对象、流程、场景、时间、职责等信息。
3. 判断回答中是否存在逻辑、语义、职业常识和心理语言异常。
4. 识别“正确但泛泛”的回答，判断用户是否缺少真实经历痕迹。
5. 根据风险严重度和置信度计算综合风险分数。
6. 根据当前风险和信息缺口动态生成下一轮追问。
7. 在对话结束后生成包含个人信息总结、关键线索、待澄清点和风险结论的评估报告。
8. 将报告和对话数据保存到云端数据库，便于后续测试和数据分析。

## 三、项目需求分析

系统需要满足以下功能需求：

1. 自然聊天能力：系统需要用相对自然、温和的语气进行提问，避免过于机械或审问式表达。
2. 多轮追问能力：系统需要支持至少 5 轮、最多 8 轮追问，并根据当前信息量和风险情况决定是否继续。
3. 信息抽取能力：系统需要从用户回答中提取事实信息，包括职业身份、岗位方向、工作内容、对象、流程、地点、时间和经历。
4. 快速预分析能力：每轮对话后快速判断当前回答是否存在明显异常、是否过于泛泛、是否需要澄清职业粒度。
5. 专家分析能力：系统需要根据情况调用语义分析、逻辑分析、职业常识分析、心理语言分析等专家节点。
6. 风险聚合能力：系统需要把不同节点的异常线索统一换算为风险值，并计算综合风险指数。
7. 动态策略决策能力：系统需要判断下一步是继续追问还是生成最终报告。
8. 追问生成能力：系统需要根据策略生成不重复、有针对性、自然的下一轮问题。
9. 报告生成能力：系统需要对整个对话过程进行总结，输出可读的风险评估报告。
10. 前端展示能力：系统需要提供网页交互界面，展示对话、风险指数、已调用专家、Agent 思考监控和最终报告。
11. 数据存储能力：系统需要把测试过程和报告保存到 Supabase，便于后续统计分析。
12. 云端部署能力：系统需要可以在 Streamlit Cloud 上运行，便于外部用户测试。

## 四、核心问题与解决思路

本项目的核心难点不是简单判断一句话是否正确，而是判断用户的职业叙述是否具有真实经历支撑。主要问题和解决思路如下。

第一，虚假身份可能回答得表面正确。很多没有真实经验的人也可以说出符合常识的职业描述，例如“心理咨询师会疏导病人情绪”“公务员要服务群众”。这些回答没有明显错误，但缺少真实细节。解决方法是引入经验密度检测，判断回答是否包含流程、边界、对象、限制、产出、卡点等真实经历痕迹。

第二，职业身份可能粒度过粗。用户说“我是公务员”“我是老师”“我是医生”时，系统不能立刻进入具体工作流程追问，而应该先澄清具体岗位类型。解决方法是在快速预分析中识别职业粗粒度问题，并将其作为追问方向信号，而不是直接作为风险分数。

第三，风险低和不确定不是同一件事。原本直接输出分数容易混淆风险严重度和判断置信度。解决方法是引入 `severity` 和 `confidence` 两个标签，再由统一公式计算风险值。

第四，多轮风险不能被最后一轮具体回答完全清零。如果用户前几轮一直泛泛回答，最后突然补充一个具体时间，系统不应该直接归零。解决方法是设计历史残余风险机制，根据泛泛回答累计次数和当前具体程度进行折扣。

第五，追问容易重复或机械。系统如果不断问同类问题，会影响测试效果。解决方法是记录历史问题，检测语义重复，并通过追问策略和润色步骤生成更自然的问题。

## 五、系统总体架构

系统整体采用 LangGraph 构建多 Agent 工作流，前端使用 Streamlit 展示，模型接口调用 DeepSeek V3，数据存储使用 Supabase。

系统主要由以下模块组成：

1. 前端交互模块：负责展示聊天页面、侧边栏状态、风险分数、专家调用情况、Agent 思考监控和最终报告。
2. 状态管理模块：负责维护对话历史、当前轮次、事实表、异常表、专家结果、风险分数和策略信息。
3. 快速预分析节点：对当前用户回答进行事实抽取、表层风险判断、经验密度判断和职业粒度判断。
4. 轻量路由节点：根据快速预分析结果决定是否调用专家，或者跳过专家直接进入风险聚合。
5. 专家分析节点：包括语义分析、逻辑分析、职业常识分析和心理语言分析，用于发现更深层异常。
6. 风险聚合节点：统一聚合快速预分析和专家节点的异常线索，计算综合风险指数。
7. 策略监督节点：根据轮次、风险、信息量和最低追问要求，决定继续追问还是生成报告。
8. 追问生成节点：根据策略生成下一轮自然问题，并避免重复追问。
9. 报告生成节点：对完整对话进行总结，输出最终风险评估报告。
10. 云端存储模块：将最终 JSON 报告同步到 Supabase 的 `output_files` 表中。

各模块之间通过统一的 `DialogueState` 状态对象传递信息，保证每一轮对话中的事实、异常、风险和策略都能被后续节点使用。

## 六、核心功能设计

系统核心功能包括以下几部分。

1. 对话交互：用户在 Streamlit 页面输入回答，系统根据当前策略生成下一轮追问。
2. 事实抽取：系统从用户回答中抽取职业身份、岗位方向、工作内容、对象、地点、时间、经历等事实。
3. 异常检测：系统检测用户回答中是否存在矛盾、回避、模糊、常识错误、语义冲突或心理语言异常。
4. 经验密度分析：系统判断用户回答是否只是表面正确，还是包含真实职业经历中的细节。
5. 职业粒度澄清：当用户只提供宽泛职业类别时，系统优先追问具体类型和职责方向。
6. 专家调用：系统根据风险和异常类型决定是否调用语义、逻辑、职业常识或心理语言专家。
7. 风险评分：系统使用 `severity` 和 `confidence` 计算单条风险值，再聚合为总风险指数。
8. 动态追问：系统根据当前主要问题选择追问策略，例如过程顺序、边界判断、真实限制、反例卡点、术语澄清和产出证据。
9. 防重复追问：系统记录历史 AI 问题，避免生成字面或语义重复的问题。
10. 报告生成：对话结束后，系统生成最终风险报告，包括个人信息总结、总体风险、关键线索和待澄清点。
11. 数据入库：系统把报告 JSON 上传到 Supabase，便于后续查询和统计。

## 七、关键技术路线

本项目采用以下技术路线：

1. LangGraph：用于构建多 Agent 节点工作流，使每个分析节点按固定顺序或条件路由执行。
2. 多 Agent 架构：将任务拆分为快速预分析、路由、专家分析、风险聚合、策略决策、追问生成和报告生成。
3. DeepSeek V3：作为核心大语言模型，用于理解用户回答、生成结构化分析、生成追问和最终报告。
4. JSON 结构化输出：要求各节点输出固定字段，便于后续状态更新和风险计算。
5. severity-confidence 风险建模：将风险严重度和判断置信度分离，再用统一公式转换为风险值。
6. Streamlit：用于构建可交互网页，包括聊天界面、侧边栏状态和 Agent 思考监控。
7. Supabase：用于保存最终报告 JSON，支持后续 SQL 查询、数据导出和统计分析。
8. dotenv 与 Streamlit Secrets：本地使用 `.env` 管理密钥，云端使用 Streamlit Secrets 管理 API Key 和数据库配置。
9. Python 数据处理：使用 Python 管理节点状态、风险计算、JSON 解析、日志保存和云端同步。

## 八、Agent 工作流程设计

每一轮用户回答后，系统按照以下流程执行：

1. 用户输入回答后，系统将回答追加到 `conversation_history`。
2. `quick_preanalysis_node` 对当前回答进行快速预分析，抽取事实、识别异常、判断经验密度和职业粒度。
3. `lightweight_routing_supervisor_node` 根据快速预分析结果决定是否调用专家节点。
4. 如果存在需要深入判断的问题，系统调用对应专家，包括语义分析、逻辑分析、职业常识分析和心理语言分析。
5. 如果只是职业粒度过粗或回答正确但泛泛，系统可以跳过专家，直接进入风险聚合和策略决策。
6. `risk_aggregator_node` 收集快速预分析和专家节点输出的异常线索，计算综合风险指数。
7. `strategy_supervisor_node` 根据当前轮次、风险分数、最低追问轮次、信息完整度和泛泛回答情况决定下一步动作。
8. 如果需要继续追问，`followup_generation_node` 根据 `followup_strategy` 生成下一轮问题。
9. 如果达到结束条件，系统调用 `report_generation_node` 生成最终报告。
10. 每一轮结束后，系统将该轮节点分析内容保存为独立 `round_record`，用于前端监控和最终 JSON 报告。

## 九、风险判断与评分机制

系统风险评分主要由三类信号组成：专家异常线索、经验密度风险和持续模糊表达风险。

专家异常线索使用 `severity` 和 `confidence` 计算：

```text
risk_value = severity_base_score * confidence_weight
```

严重度基础分：

```text
CRITICAL = 45.0
HIGH     = 25.0
MEDIUM   = 10.0
LOW      = 3.0
```

置信度权重：

```text
CRITICAL = 1.0
HIGH     = 0.8
MEDIUM   = 0.5
LOW      = 0.2
```

多条风险值使用独立风险叠加：

```text
LieIndex = 100 * (1 - product(1 - risk_value / 100))
```

经验密度风险用于处理“正确但泛泛”的回答：

```text
单轮低经验密度：risk_value = 8.0
连续泛泛 >= 2 轮：risk_value = 16.0
连续泛泛 >= 3 轮或累计泛泛 >= 4 次：risk_value = 20.0
连续泛泛 >= 4 轮或累计泛泛 >= 5 次：risk_value = 24.0
```

历史残余风险用于防止前几轮泛泛回答被最后一轮具体回答完全清零：

```text
累计泛泛 >= 5 次：base = 18.0
累计泛泛 >= 3 次：base = 16.0
累计泛泛 = 2 次：base = 12.0
累计泛泛 = 1 次：base = 8.0
```

再根据当前具体程度折扣：

```text
specificity_level = HIGH   -> factor = 0.65
specificity_level = MEDIUM -> factor = 0.8
specificity_level = LOW    -> factor = 1.0
```

最终：

```text
residual_risk = max(3.0, base * factor)
```

职业粒度过粗本身不直接加风险分，而是作为追问方向信号：

```text
type = role_disambiguation
severity = LOW
confidence = HIGH
risk_value = 0.0
```

## 十、数据收集与测试方案

测试数据主要来自项目云端部署后邀请同学和朋友进行模拟测试。测试者可以选择使用真实职业身份，也可以有意捏造一个职业身份。系统会记录每轮对话、节点分析结果、最终风险分数和最终报告。

测试时需要人工额外记录以下信息：

1. 测试者是否有意捏造职业身份。
2. 系统最终风险分数是多少。
3. 系统是否成功识别出风险。
4. 风险来源是逻辑异常、语义异常、职业常识异常、心理语言异常，还是经验密度不足。
5. 是否存在误判或漏检。

测试数据会被保存到 Supabase 中的 `output_files` 表。当前系统只上传 `outputs/reports` 下的 JSON 文件，不上传 logs 和 markdown 文件，以减少重复数据。后续可以通过 SQL 查询 `content_json` 字段，导出每轮对话、最终报告和风险分数，形成测试统计表。

## 十一、系统部署方案

系统部署采用 Streamlit Cloud + Supabase + DeepSeek API 的方案。

前端部署：

- Repository：`career-lie-index-v3`
- Branch：`main`
- Main file path：`v3/app.py`
- 部署平台：Streamlit Cloud

数据库部署：

- 使用 Supabase 免费版
- 建立 `output_files` 表
- 字段包括 `source_path`、`category`、`filename`、`file_ext`、`content_json`、`raw_content`、`uploaded_at` 等
- 用于保存最终报告 JSON

模型接口：

- 使用 DeepSeek 官方 API
- 本地通过 `.env` 配置 `DEEPSEEK_API_KEY`
- 云端通过 Streamlit Secrets 配置 `DEEPSEEK_API_KEY`、`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY` 等密钥

数据同步：

- 本地可运行上传脚本将历史 outputs 上传到 Supabase
- 云端运行时在生成最终报告后自动同步报告 JSON

## 十三、项目创新点

本项目相比普通聊天机器人或简单测评系统，主要有以下创新点：

1. 不是只生成聊天回复，而是构建了多 Agent 分析工作流。
2. 将职业身份一致性检测拆分为事实抽取、异常检测、专家分析、风险聚合和策略决策。
3. 引入 `severity` 和 `confidence`，避免把风险低和不确定混为一谈。
4. 引入经验密度检测，用来识别“正确但泛泛”的虚假职业回答。
5. 引入历史残余风险，避免用户最后补充一点细节后系统直接清零。
6. 对职业粒度过粗进行特殊处理，先澄清岗位类型，再进入深层职业追问。
7. 追问策略不是固定模板，而是根据当前风险和信息缺口动态生成。
8. 系统可以自动生成结构化最终报告，而不是只给出单一分数。
9. 通过 Supabase 保存 JSON 报告，为后续数据分析和模型优化提供基础。

## 十四、存在问题与改进方向

当前系统仍然存在一些不足：

1. 模型有时会把真实但简短的回答误判为泛泛回答，需要继续优化短回答识别。
2. 对不同职业的常识覆盖还不够完整，部分小众职业可能判断不稳定。
3. 追问自然度仍需优化，避免问题过于像面试或审问。
4. 模型偶尔会生成不准确或不专业的词汇，需要通过整体润色和语境约束改善。
5. 对“高水平伪装者”的识别还需要更多真实测试数据验证。
6. 当前测试数据量较小，仍需要扩展样本规模。
7. 最终报告的表达和结构还可以进一步增强，使其更适合展示和分析。
8. 风险分数权重仍需要根据测试集结果继续校准，减少误判和漏检。
